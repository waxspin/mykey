# Deviations from RFC 3830

mykey implements the RFC 3830 wire format and key derivation, but it is not a
complete or fully interoperable MIKEY implementation. This page records every
place where it knowingly departs from the RFC, and why. If you are evaluating
mykey for interoperability with another MIKEY stack, read this page first.

## Summary

| Area | Status |
|---|---|
| PRF (§4.1.2) | Compliant |
| Key derivation labels (§4.1.3, §4.1.4) | Compliant |
| "Last payload" value (§6.1) | **Deviates** — uses 255 where the RFC assigns 0; breaks every outbound message |
| TGK construction | **Deviates** — derived through the PRF rather than used raw |
| DH method (§3.3) | **Deviates** — X25519, and no SIGN payload; §3.3 is a non-goal |
| PSK method (§3.1) | **Incomplete** — NULL encryption only; MAC not verified on receive |
| Timestamps (§4.2.8, §6.6) | **Deviates** — COUNTER (optional type) rather than the mandatory NTP types; no replay handling; type 1 length wrong |
| Key data sub-payload (§6.13) | Not implemented — the TGK is written as bare bytes |
| Verification message (§6.9) | Not implemented — no mutual authentication |
| Public-key method (§3.2) | Not implemented |

Interoperability work is planned: pre-shared key mode to §3.1 compliance, then
OAKLEY groups, then RFC 4650 (MIKEY-DHHMAC) for authenticated DH. X25519 stays as
the default where interoperability is not needed. §3.3 signed DH is out of scope —
see [The missing signatures](#the-missing-signatures) below.

## TGK construction

RFC 3830 never derives the TGK through the PRF. In the DH method the TGK *is*
the raw DH result `g^(xi*xr)` (§3.3), and in the pre-shared key method the TGK is
generated by the initiator and transported inside the KEMAC payload (§3.1).

mykey instead computes `TGK = PRF(inkey, "TGK" || RAND)` in both cases, where
`inkey` is the X25519 shared secret or the pre-shared key. Because this step has
no counterpart in the RFC it has no RFC constant, so it uses an ASCII label — the
only label in the crate that is not an RFC label.

These are really two deviations with different justifications, and only one of
them survives.

### In pre-shared key mode: not defensible, and slated for removal

RFC §3.1 PSK is key *transport*. The initiator chooses a TGK at random and sends
it encrypted; the responder decrypts it. mykey has both sides derive the same TGK
deterministically from the pre-shared key, which has three consequences:

- **It cannot interoperate.** A conformant peer transmits a random encrypted TGK;
  mykey ignores `enc_data` and derives its own. The two never agree on a key.
- **It is why the TGK is on the wire in the clear.** The field is vestigial
  precisely *because* the receiver re-derives, which is the root of the
  confidentiality problem described under
  [Pre-shared key mode](#pre-shared-key-mode).
- **It concentrates all session freshness in RAND.** The SRTP master key becomes a
  pure function of (PSK, RAND, `cs_id`, `csb_id`), so a RAND collision is an exact
  master-key repeat — and for AES-CM, keystream reuse. With 16 random bytes from
  `OsRng` the birthday bound is around 2⁶⁴ sessions, so this is not a practical
  break. But the RFC's random-TGK design degrades gracefully where this does not:
  if RAND were ever weakened, the RFC design still yields an independently random
  TGK.

Bringing PSK mode to §3.1 compliance removes this deviation entirely rather than
documenting it.

### In an OAKLEY/DHHMAC mode: must not be carried over

RFC 4650 specifies that both parties "calculate the TGK as `g^(xi * xr)`", with
processing per RFC 3830 §4. An authenticated-DH mode must therefore use the raw
DH result, with no PRF wrapping.

### In X25519 mode: the deviation is correct, and compliance is not an option

Here the choice is not between deviating and complying. §3.3's `TGK = g^(xi*xr)`
was written for MODP groups; applied literally to X25519 it means using the raw
32-byte curve output directly as key material, and
[RFC 7748](https://datatracker.ietf.org/doc/rfc7748/) §6.1 says not to — "Alice
and Bob can then use a key-derivation function that includes K, K_A, and K_B to
derive a symmetric key."

Since no elliptic-curve group is registered for MIKEY at all, there is no
conformant X25519 mode to conform to. Running the shared secret through the PRF
is simply the better of the two available options, and it costs nothing because
this mode is private-use regardless.

Two refinements are outstanding, both from RFC 7748:

- **The public keys are not bound into the derivation.** `derive_tgk` takes the
  shared secret and RAND only. RFC 7748 §6.1 asks for `K_A` and `K_B` as well,
  and §7 explains why: equivalent public keys yield identical shared secrets, so
  "using a public key as an identifier and knowledge of a shared secret as proof
  of ownership (without including the public keys in the key derivation) might
  lead to subtle vulnerabilities" — which is exactly what
  [peer pinning](../identity/overview.md) does. `PinnedPeer::verify` compares all
  32 bytes exactly, so a substituted equivalent encoding is rejected by the pin
  itself; this is a robustness gap rather than a known exploit.
- **There is no contributory check.** Neither `was_contributory()` nor an
  all-zero test is called anywhere, so a small-order peer value "will eliminate
  any contribution from the other party's private key" (§7) and yield a
  predictable TGK.

Everything downstream of the TGK (the SRTP master key and salt) follows §4.1.3
exactly.

## Diffie-Hellman: X25519, and no signatures

Two separate deviations, of which the second is the one that matters.

### The group

RFC 3830 §4.2.7 mandates OAKLEY 5 (1536-bit MODP) for the DH method, with OAKLEY
1 and 2 optional. mykey uses X25519 and signals it with DH-Group value `255`.

IANA's MIKEY DH-Group registry has only ever contained the three OAKLEY groups;
values 241–255 are Reserved for Private Use, so `255` is a legitimate private
code point rather than a squatted one. No elliptic-curve group has ever been
registered for MIKEY.

OAKLEY support is planned, but as an **opt-in** rather than a replacement. OAKLEY
5 offers roughly 96-bit security — below the 112-bit floor NIST has required for
new systems since 2014 — against X25519's ~128, and as a single fixed universal
group it is the shape of problem that makes Logjam-style precomputation attacks
amortize. Implementing it also means constant-time modular exponentiation plus
peer-key validation (range checks and small-subgroup rejection) that X25519
provides inherently.

Adopting OAKLEY is therefore a deliberate security downgrade accepted in exchange
for interoperability. X25519 remains the default for deployments that do not need
to talk to another MIKEY stack.

### The missing signatures

More fundamentally, the RFC's DH method is signature-authenticated:

```text
I_MESSAGE = HDR, T, RAND, [IDi|CERTi], [IDr], {SP}, DHi, SIGNi
R_MESSAGE = HDR, T, [IDr|CERTr], IDi, DHr, DHi, SIGNr
```

`SIGNi` and `SIGNr` cover the whole message and are what prevent a
man-in-the-middle from substituting DH values. mykey performs **unauthenticated**
ephemeral DH and emits no SIGN or CERT payload at all.

This means DH mode could not interoperate with a compliant implementation even
if the group matched — a conformant peer would reject the message for the
missing signature. Switching to OAKLEY 5 on its own would buy no interoperability
whatsoever, only the security and implementation costs above. That is why OAKLEY
is planned alongside an authenticated DH mode rather than on its own.

**Implementing §3.3 itself is an explicit non-goal.** It requires RSA PKCS#1 v1.5
signatures (mandatory), RSASSA-PSS (recommended), X.509 certificate handling, and
the §4.3 certificate policy and authorization rules. Instead, authenticated DH
will be provided by [RFC 4650](https://datatracker.ietf.org/doc/rfc4650/)
(MIKEY-DHHMAC, data types 7 and 8), which authenticates the exchange with an
HMAC keyed from a pre-shared secret rather than with signatures. DHHMAC is
standards track, reuses RFC 3830's PRF and DH groups, and needs no PKI.

mykey's current answer to the MITM exposure is [peer key
pinning](../identity/overview.md), which is opt-in and trust-on-first-use rather
than PKI-based. See also the limitations noted in [Ephemeral
DH](../key-exchange/ephemeral-dh.md).

Note that §3.3 makes the DH method OPTIONAL to implement, and §4.2.7 conditions
OAKLEY 5 on DH "when supported" — so these deviations cost no conformance claim
that mykey would otherwise have.

Also note that MIKEY has no key-management-method negotiation: the `data type`
field in the common header declares the method outright, and error 11 ("Invalid
DT") is the only method-level signal. The capability discovery of §5.1.1 covers
SRTP *policy parameters*, not the keying method. Supporting several methods
therefore means a responder accepting several data types by explicit
configuration — never an automatic downgrade, which would itself be an attack.

## Pre-shared key mode

`new_psk_init` builds its KEMAC with NULL encryption (`EncAlg::Null`) and places
the TGK in `enc_data` in the clear. RFC 3830 §4.2.3 permits NULL encryption only
where "the underlying protocols can guarantee security" and warns to use it with
caution; an SDP file or a SAP announcement is not such a channel.

> **Warning:** anyone who can read a mykey PSK-Init message can recover the TGK
> and therefore the SRTP master key, without knowing the pre-shared key. Do not
> use PSK mode over a channel you would not be willing to send the SRTP key over
> directly.

RFC-correct PSK mode requires encrypting the TGK under an encryption key derived
per §4.1.4 (AES-CM, §4.2.3), which needs a block cipher mykey does not currently
depend on. `derive_enc_key` already produces the correct key for this.

Separately, no receive path verifies the KEMAC MAC. `new_psk_init` computes and
appends one, but `from_bytes` and `complete_psk` do not check it, so it currently
provides no integrity protection on ingest.

## Timestamps and replay protection

RFC 3830 defines three timestamp types (§6.6, Table 6.6): NTP-UTC (0) and NTP (1)
are **mandatory** and 64 bits wide; COUNTER (2) is **optional** and 32 bits.

mykey emits COUNTER, with the CSB ID as the counter value. It implements none of
the replay handling the timestamp exists to support (§5.4) — nothing records seen
timestamps or RAND values, so a captured message can be replayed.

`TimestampType::value_len()` also reports 4 bytes for type 1 (`NtpShort`), where
Table 6.6 specifies 64 bits. Because `parse_timestamp` uses that length both to
slice the value and to advance the payload cursor, a message carrying a type 1
timestamp is read four bytes short and every following payload is parsed from the
wrong offset.

Measured behaviour, for the avoidance of doubt: type 0 (NTP-UTC) and type 2
(COUNTER) parse correctly; only type 1 is affected, and it fails closed with a
parse error rather than silently accepting the misaligned data. The enum variant
name is also a misnomer — Table 6.6 type 1 is "NTP" at 64 bits, not a short form.

## The "Last payload" terminator

This is the single most consequential wire-format deviation, and it affects every
message in every mode.

RFC 3830 Table 6.1.b assigns **0** to "Last payload", the value that terminates a
payload chain. The table contains no entry for the common header, since `HDR` is
never a `Next Payload` value.

mykey declares `PayloadType::Last = 255` and maps `0` to `PayloadType::Hdr`.
Value 255 is not defined by Table 6.1.b at all.

- **Outbound messages are non-conformant.** Every chain mykey emits is terminated
  with `0xFF`. A conformant peer reads 255, finds no such entry in Table 6.1.b,
  and rejects the message.
- **Inbound parsing succeeds only by accident.** The parse loop is
  `while next != 255 && pos < data.len()`, so a conformant `0` terminator is never
  recognised as one — parsing stops because the cursor reached the end of the
  buffer. Any message whose payload chain ends before the buffer does instead
  reaches `PayloadType::from_u8(0)`, resolves it to `Hdr`, and fails with
  `InvalidPayloadType(0)`.

Fixing this means setting `Last = 0`, removing `Hdr` from the `Next Payload`
mapping, and terminating on the value rather than on buffer exhaustion. It is a
one-byte change on the wire and a breaking one, so it belongs with the rest of
the interoperability work.

## Key data sub-payload

RFC 3830 §6.13 gives key material inside KEMAC a structure: a `Next Payload`,
`Type` and `KV` nibbles, an explicit `Key data len`, and optional salt and key
validity fields. One KEMAC may carry several such sub-payloads.

mykey writes the TGK into `enc_data` as bare bytes with none of this framing, so
even with encryption in place the payload would not parse as a conformant KEMAC.

## Verification message

The pre-shared key and public-key methods use a verification message (`V`, §6.9;
data type 1) so the responder can prove possession of the key — this is what
provides mutual authentication. The initiator requests it via a flag in the
common header.

`VerificationPayload` and `PayloadType::V` exist and parse, but nothing builds a
verification message and nothing checks one, and the header flag is never set.
PSK mode is therefore one-way: the initiator learns nothing about the responder.

## Public-key mode

The public-key encryption method of §3.2 is not implemented. `PayloadType::Sign`
and `PayloadType::Cert` exist as enum discriminants for wire-format completeness,
but there are no corresponding payload types, and nothing parses, serializes, or
verifies them.

## What *is* interoperable

The PRF (§4.1.2) and the key derivation labels and constants (§4.1.3 and §4.1.4)
follow the RFC. The individual payload layouts and the common header fields are
also as specified — but note that the "Last payload" terminator above means no
message mykey *emits* is currently conformant, however correct its individual
payloads are.

Pre-shared key mode is the realistic path to interoperability, once the
terminator, KEMAC encryption, sub-payload framing, and MAC verification gaps are
closed. It is also the only method RFC 3830 makes mandatory to implement, so it
is the one any other MIKEY stack is guaranteed to support.

Note that RFC 3830 publishes no test vectors, so conformance of the derivation
chain can only be confirmed by testing against another implementation.
