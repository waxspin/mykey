# Deviations from RFC 3830

mykey implements the RFC 3830 wire format and key derivation, but it is not a
complete or fully interoperable MIKEY implementation. This page records every
place where it knowingly departs from the RFC, and why. If you are evaluating
mykey for interoperability with another MIKEY stack, read this page first.

## Summary

| Area | Status |
|---|---|
| PRF (§4.1.2) | Compliant |
| Key derivation labels (§4.1.3, §4.1.4) | Compliant |
| TGK construction | **Deviates** — derived through the PRF rather than used raw |
| DH method (§3.3) | **Deviates** — X25519, and no SIGN payload |
| PSK method (§3.1) | **Incomplete** — NULL encryption only; MAC not verified on receive |
| Public-key method (§3.2) | Not implemented |

## TGK construction

RFC 3830 never derives the TGK through the PRF. In the DH method the TGK *is*
the raw DH result `g^(xi*xr)` (§3.3), and in the pre-shared key method the TGK is
generated by the initiator and transported inside the KEMAC payload (§3.1).

mykey instead computes `TGK = PRF(inkey, "TGK" || RAND)` in both cases, where
`inkey` is the X25519 shared secret or the pre-shared key.

The reason is that a raw X25519 shared secret is a curve point, not uniformly
distributed key material, and should be run through a KDF before use. Because
this step has no counterpart in the RFC it has no RFC constant, so it uses an
ASCII label — the only label in the crate that is not an RFC label.

Everything downstream of the TGK (the SRTP master key and salt) follows §4.1.3
exactly.

## Diffie-Hellman: X25519, and no signatures

Two separate deviations, of which the second is the one that matters.

### The group

RFC 3830 §4.2.7 mandates OAKLEY 5 (1536-bit MODP) for the DH method, with OAKLEY
1 and 2 optional. mykey uses X25519 and signals it with DH-Group value `255`.

IANA's MIKEY DH-Group registry has only ever contained the three OAKLEY groups;
values 241–255 are Reserved for Private Use, so `255` is a legitimate private
code point rather than a squatted one. No elliptic-curve group has ever been
registered for MIKEY.

We do not intend to switch to OAKLEY 5. It offers roughly 96-bit security —
below the 112-bit floor NIST has required for new systems since 2014 — against
X25519's ~128, and as a single fixed universal group it is the shape of problem
that makes Logjam-style precomputation attacks amortize. Implementing it also
means constant-time modular exponentiation plus peer-key validation (range
checks and small-subgroup rejection) that X25519 provides inherently.

### The missing signatures

More fundamentally, the RFC's DH method is signature-authenticated:

```text
I_MESSAGE = HDR, T, RAND, [IDi|CERTi], [IDr], {SP}, DHi, SIGNi
R_MESSAGE = HDR, T, [IDr|CERTr], IDi, DHr, DHi, SIGNr
```

`SIGNi` and `SIGNr` cover the whole message and are what prevent a
man-in-the-middle from substituting DH values. mykey performs **unauthenticated**
ephemeral DH and emits no SIGN or CERT payload at all.

This means DH mode could not interoperate with a compliant implementation even
if the group matched — a conformant peer would reject the message for the
missing signature. Switching to OAKLEY 5 on its own would buy no interoperability
whatsoever, only the security and implementation costs above.

mykey's answer to the MITM exposure is [peer key
pinning](../identity/overview.md), which is opt-in and trust-on-first-use rather
than PKI-based. See also the limitations noted in [Ephemeral
DH](../key-exchange/ephemeral-dh.md).

Note that §3.3 makes the DH method OPTIONAL to implement, and §4.2.7 conditions
OAKLEY 5 on DH "when supported" — so these deviations cost no conformance claim
that mykey would otherwise have.

## Pre-shared key mode

`new_psk_init` builds its KEMAC with NULL encryption (`EncAlg::Null`) and places
the TGK in `enc_data` in the clear. RFC 3830 §4.2.3 permits NULL encryption only
where "the underlying protocols can guarantee security" and warns to use it with
caution; an SDP file or a SAP announcement is not such a channel.

> **Warning:** anyone who can read a mykey PSK-Init message can recover the TGK
> and therefore the SRTP master key, without knowing the pre-shared key. Do not
> use PSK mode over a channel you would not be willing to send the SRTP key over
> directly.

RFC-correct PSK mode requires encrypting the TGK under an encryption key derived
per §4.1.4 (AES-CM, §4.2.3), which needs a block cipher mykey does not currently
depend on. `derive_enc_key` already produces the correct key for this.

Separately, no receive path verifies the KEMAC MAC. `new_psk_init` computes and
appends one, but `from_bytes` and `complete_psk` do not check it, so it currently
provides no integrity protection on ingest.

## Public-key mode

The public-key encryption method of §3.2 is not implemented. `PayloadType::Sign`
and `PayloadType::Cert` exist as enum discriminants for wire-format completeness,
but there are no corresponding payload types, and nothing parses, serializes, or
verifies them.

## What *is* interoperable

The PRF (§4.1.2), the key derivation labels and constants (§4.1.3 and §4.1.4),
the common header, and the payload wire formats all follow the RFC. Pre-shared
key mode is the realistic path to interoperability with another implementation,
once the KEMAC encryption and MAC verification gaps above are closed.

Note that RFC 3830 publishes no test vectors, so conformance of the derivation
chain can only be confirmed by testing against another implementation.
