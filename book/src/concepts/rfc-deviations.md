# Deviations from RFC 3830

mykey implements the RFC 3830 wire format and key derivation, but it is not a
complete or fully interoperable MIKEY implementation. This page records every
place where it knowingly departs from the RFC, and why. If you are evaluating
mykey for interoperability with another MIKEY stack, read this page first.

## Summary

| Area | Status |
|---|---|
| PRF (§4.1.2) | Compliant |
| Key derivation labels (§4.1.3, §4.1.4) | Compliant |
| "Last payload" value (§6.1) | Compliant — fixed; was 255 where the RFC assigns 0 |
| TGK construction | **Deviates for X25519 only** — PRF-derived per RFC 7748 §6.1; MODP groups use the raw DH result as the RFC requires |
| DH method (§3.3) | **Partial** — OAKLEY groups 1/2/5 implemented, X25519 still the default; no SIGN payload, which §3.3 requires |
| DHHMAC (RFC 4650) | Implemented — authenticated DH with no PKI; **deviates from RFC 4650 §4.2's KEMAC encodings**, which contradict RFC 3830 |
| PSK method (§3.1) | Compliant — fixed; random TGK transported under AES-CM, MAC verified on receive |
| Key data sub-payload (§6.13) | Compliant — fixed |
| Verification message (§6.9) | Compliant — fixed; opt-in via the V flag |
| Timestamps (§4.2.8, §6.6) | **Deviates** — emits COUNTER (the optional type) rather than a mandatory NTP type |
| Replay protection (§5.4) | Not implemented — no record of seen timestamps or RAND values |
| Public-key method (§3.2) | Not implemented |

Interoperability work is planned: pre-shared key mode to §3.1 compliance, then
OAKLEY groups, then RFC 4650 (MIKEY-DHHMAC) for authenticated DH. X25519 stays as
the default where interoperability is not needed. §3.3 signed DH is out of scope —
see [The missing signatures](#the-missing-signatures) below.

## TGK construction

RFC 3830 never derives the TGK through the PRF. In the DH method the TGK *is*
the raw DH result `g^(xi*xr)` (§3.3), and in the pre-shared key method the TGK is
generated by the initiator and transported inside the KEMAC payload (§3.1).

mykey instead computes `TGK = PRF(inkey, "TGK" || RAND)` in both cases, where
`inkey` is the X25519 shared secret or the pre-shared key. Because this step has
no counterpart in the RFC it has no RFC constant, so it uses an ASCII label — the
only label in the crate that is not an RFC label.

These are really two deviations with different justifications, and only one of
them survives.

### In pre-shared key mode: not defensible, and slated for removal

RFC §3.1 PSK is key *transport*. The initiator chooses a TGK at random and sends
it encrypted; the responder decrypts it. mykey has both sides derive the same TGK
deterministically from the pre-shared key, which has three consequences:

- **It cannot interoperate.** A conformant peer transmits a random encrypted TGK;
  mykey ignores `enc_data` and derives its own. The two never agree on a key.
- **It is why the TGK is on the wire in the clear.** The field is vestigial
  precisely *because* the receiver re-derives, which is the root of the
  confidentiality problem described under
  [Pre-shared key mode](#pre-shared-key-mode).
- **It concentrates all session freshness in RAND.** The SRTP master key becomes a
  pure function of (PSK, RAND, `cs_id`, `csb_id`), so a RAND collision is an exact
  master-key repeat — and for AES-CM, keystream reuse. With 16 random bytes from
  `OsRng` the birthday bound is around 2⁶⁴ sessions, so this is not a practical
  break. But the RFC's random-TGK design degrades gracefully where this does not:
  if RAND were ever weakened, the RFC design still yields an independently random
  TGK.

Bringing PSK mode to §3.1 compliance removes this deviation entirely rather than
documenting it.

### In an OAKLEY/DHHMAC mode: must not be carried over

RFC 4650 specifies that both parties "calculate the TGK as `g^(xi * xr)`", with
processing per RFC 3830 §4. An authenticated-DH mode must therefore use the raw
DH result, with no PRF wrapping.

### In MODP mode: raw, as the RFC requires

For the OAKLEY groups the TGK **is** the raw DH result, with no PRF wrapping.
§3.3 states this directly, and RFC 4650 repeats it for DHHMAC.

This matters more than it looks. A conformant peer computes the raw value and
feeds it to the §4.1.3 derivation; wrapping it first would make our TGK differ
from theirs, so key agreement would fail — silently, in the usual way. It would
destroy the only thing OAKLEY is here for.

> **Note for future work:** there is deliberately no `derive_tgk_modp`. Adding
> one for symmetry with `derive_tgk_x25519` would look tidy and would be an
> interop break. The MODP path must pass the shared secret through unchanged.

Raw does not mean unprotected. The TGK is only ever PRF *input* — `derive_srtp_keys`
feeds it to the §4.1.2 PRF under the §4.1.3 labels, which bind `cs_id` and
`csb_id`. So in both modes the DH output is run through a KDF before it becomes
an SRTP key:

```text
MODP:    shared → TGK (raw) ───────────────→ §4.1.3 PRF → SRTP keys
X25519:  shared → PRF(+K_A,K_B) → TGK ─────→ §4.1.3 PRF → SRTP keys
```

The difference is only whether an extra extraction step, with the public keys
bound in, happens first.

### In X25519 mode: the deviation is correct, and compliance is not an option

Here the choice is not between deviating and complying. §3.3's `TGK = g^(xi*xr)`
was written for MODP groups; applied literally to X25519 it means using the raw
32-byte curve output directly as key material, and
[RFC 7748](https://datatracker.ietf.org/doc/rfc7748/) §6.1 says not to — "Alice
and Bob can then use a key-derivation function that includes K, K_A, and K_B to
derive a symmetric key."

Since no elliptic-curve group is registered for MIKEY at all, there is no
conformant X25519 mode to conform to. Running the shared secret through the PRF
is simply the better of the two available options, and it costs nothing because
this mode is private-use regardless.

Two refinements from RFC 7748 have since been applied:

- **Both public keys are bound into the derivation**, as §6.1 asks:

  ```text
  TGK = PRF(K, "MIKEY-X25519-TGK" || K_initiator || K_responder || RAND)
  ```

  §7 explains why it matters: equivalent public keys yield identical shared
  secrets, so "using a public key as an identifier and knowledge of a shared
  secret as proof of ownership (without including the public keys in the key
  derivation) might lead to subtle vulnerabilities" — which is exactly what
  [peer pinning](../identity/overview.md) does. (`PinnedPeer::verify` compares
  all 32 bytes exactly, so a substituted equivalent encoding was already
  rejected by the pin itself; this closed a robustness gap, not a known
  exploit.)

  The keys are ordered by **protocol role** rather than by who is calling, so an
  initiator and a responder independently build the same label. Ordering by
  "own, then peer" would have produced two different labels and no agreement.

- **Small-order peer values are rejected.** `was_contributory()` is now checked
  in both `DhKeyPair::diffie_hellman` and `Identity::diffie_hellman`, so a peer
  cannot force an all-zero shared secret that it can predict (§7: such a value
  "will eliminate any contribution from the other party's private key").
  Checking is optional in §6.1; mykey rejects with `InvalidDhValue`.

MODP mode gets no such binding, since the RFC fixes the TGK. The RFC 7748 §7
concern is specific to Curve25519's cofactor and non-canonical encodings and
does not carry over to a safe-prime MODP group, where the subgroup validation
described above covers the analogous attack.

Everything downstream of the TGK (the SRTP master key and salt) follows §4.1.3
exactly.

## Diffie-Hellman: X25519, and no signatures

Two separate deviations, of which the second is the one that matters.

### The group

RFC 3830 §4.2.7 mandates OAKLEY 5 (1536-bit MODP) for the DH method, with OAKLEY
1 and 2 optional. mykey uses X25519 and signals it with DH-Group value `255`.

IANA's MIKEY DH-Group registry has only ever contained the three OAKLEY groups;
values 241–255 are Reserved for Private Use, so `255` is a legitimate private
code point rather than a squatted one. No elliptic-curve group has ever been
registered for MIKEY.

OAKLEY groups 1 (768-bit), 2 (1024-bit) and 5 (1536-bit) are implemented as an
**opt-in**, via `ModpInitiator` / `ModpResponder`. X25519 remains the default.

Adopting OAKLEY is a deliberate security downgrade accepted in exchange for
interoperability. OAKLEY 5 offers roughly 90–120 bits of strength (RFC 3526 §8)
against X25519's ~128, and all three are single fixed universal groups where
precomputation amortises across every session.

Peer values receive NIST SP 800-56A full public key validation for safe-prime
groups: `1 < y < p-1`, plus `y^q mod p == 1` to confirm membership in the
order-`q` subgroup generated by 2. The second check costs a full exponentiation
and is what closes small-subgroup confinement; it is not skipped.

The ephemeral private exponent is 256 bits, above the 180–240 bits RFC 3526 §8
recommends for the strongest group offered here.

### The missing signatures

More fundamentally, the RFC's DH method is signature-authenticated:

```text
I_MESSAGE = HDR, T, RAND, [IDi|CERTi], [IDr], {SP}, DHi, SIGNi
R_MESSAGE = HDR, T, [IDr|CERTr], IDi, DHr, DHi, SIGNr
```

`SIGNi` and `SIGNr` cover the whole message and are what prevent a
man-in-the-middle from substituting DH values. mykey performs **unauthenticated**
ephemeral DH and emits no SIGN or CERT payload at all.

This means DH mode could not interoperate with a compliant implementation even
if the group matched — a conformant peer would reject the message for the
missing signature. Switching to OAKLEY 5 on its own would buy no interoperability
whatsoever, only the security and implementation costs above. That is why OAKLEY
is planned alongside an authenticated DH mode rather than on its own.

**Implementing §3.3 itself is an explicit non-goal.** It requires RSA PKCS#1 v1.5
signatures (mandatory), RSASSA-PSS (recommended), X.509 certificate handling, and
the §4.3 certificate policy and authorization rules. Instead, authenticated DH
will be provided by [RFC 4650](https://datatracker.ietf.org/doc/rfc4650/)
(MIKEY-DHHMAC, data types 7 and 8), which authenticates the exchange with an
HMAC keyed from a pre-shared secret rather than with signatures. DHHMAC is
standards track, reuses RFC 3830's PRF and DH groups, and needs no PKI.

mykey's current answer to the MITM exposure is [peer key
pinning](../identity/overview.md), which is opt-in and trust-on-first-use rather
than PKI-based. See also the limitations noted in [Ephemeral
DH](../key-exchange/ephemeral-dh.md).

Note that §3.3 makes the DH method OPTIONAL to implement, and §4.2.7 conditions
OAKLEY 5 on DH "when supported" — so these deviations cost no conformance claim
that mykey would otherwise have.

Also note that MIKEY has no key-management-method negotiation: the `data type`
field in the common header declares the method outright, and error 11 ("Invalid
DT") is the only method-level signal. The capability discovery of §5.1.1 covers
SRTP *policy parameters*, not the keying method. Supporting several methods
therefore means a responder accepting several data types by explicit
configuration — never an automatic downgrade, which would itself be an attack.

## DHHMAC (RFC 4650) and two defects in its text

RFC 4650 adds HMAC-authenticated Diffie-Hellman: the DH half-keys are
authenticated with an HMAC keyed from a pre-shared secret instead of a
signature, which gives forward secrecy and mutual authentication with no PKI.
It is standards track, reuses RFC 3830's PRF and DH groups, and is registered
as data types 7 and 8. mykey implements it via `DhHmacInitiator` /
`DhHmacResponder`.

Two statements in RFC 4650 §4.2 contradict RFC 3830 §6.2, which normatively
defines the KEMAC field encodings. **mykey follows RFC 3830.**

| Field | RFC 3830 §6.2 | RFC 4650 §4.2 |
|---|---|---|
| `Encr alg` NULL | 0 | "set to 2 (NULL)" |
| `MAC alg` NULL | 0 | 1 |
| `MAC alg` HMAC-SHA-1-160 | 1 | 0 |

The `Encr alg` claim is self-contradictory: value 2 is AES-KW-128 in Table
6.2.a, and the same RFC 4650 paragraph says "The AES key wrap method SHALL not
be applied for DHHMAC".

The `MAC alg` swap is **security-relevant**. A peer following RFC 4650 literally
sends `MAC alg = 0` meaning "HMAC-SHA-1 present"; a reader following RFC 3830
sees NULL — no MAC — and would skip verification. That is
GHSA-xq78-wvcv-hqvj reintroduced through a typo. mykey therefore does **not**
accept `MAC alg = 0` as a MAC: it is NULL, and NULL is refused. Against a
literal-RFC-4650 peer the exchange fails loudly rather than silently
unauthenticated, which is the correct trade.

Implementations agree with RFC 3830 rather than RFC 4650:

| Implementation | DHHMAC | `Encr` NULL | `MAC` NULL | HMAC-SHA-1-160 |
|---|---|---|---|---|
| libmikey (minisip) | performs it | 0 | 0 | 1 |
| Wireshark | dissects it | 0 | 0 | 1 |
| GStreamer | not implemented | 0 | 0 | 1 |

RFC 4650 also cites "[RFC 3830] sections 4.1.3 and 4.1.5" for the `auth_key`
derivation; RFC 3830 has no §4.1.5. The relevant section is §4.1.4, and
libmikey confirms it — `KeyAgreementDHHMAC` extends `KeyAgreementPSK` and
derives the key as `0x2D22AC75 || 0xFF || csb_id || RAND` over the pre-shared
secret, which is exactly mykey's `derive_auth_key`.

None of this is covered by the 15 errata filed against RFC 4650, all of which
are editorial.

### Payload order

RFC 4650 Figure 1 gives `HDR, T, RAND, [IDi], IDr, {SP}, DHi, KEMAC`; libmikey
emits `HDR, T, {SP}, RAND, DH, KEMAC` and omits the ID payloads entirely,
despite the RFC saying the initiator "SHALL always include the recipient's
identity". Order does not affect interoperability — payloads are chained by
`next_payload`, so any order parses, and each side computes the MAC over its own
serialized bytes. mykey follows the RFC's order and does not send ID payloads.

## Pre-shared key mode — fixed

mykey ≤ 1.0.0 derived the TGK from the pre-shared key on both sides and built its
KEMAC with NULL encryption, placing the TGK in `enc_data` in the clear. Anyone who
could read a PSK-Init recovered the SRTP master key without knowing the PSK, and
no receive path verified the MAC. Both are now fixed.

PSK mode follows §3.1 as key *transport*: the initiator generates a random TGK,
frames it as a Key data sub-payload (§6.13), and encrypts it with AES-CM (§4.2.3)
under an encryption key and 112-bit salt derived from the pre-shared key (§4.1.4).
The IV is built as the RFC specifies:

```text
IV = (S XOR (0x0000 || CSB ID || T)) || 0x0000
```

On receive, the message MAC is verified **before** any decryption, so a message
that fails authentication produces no key material. A `MacAlg::Null` payload, an
absent MAC, and a truncated MAC are all refused rather than treated as "no check
required".

This is a breaking change against 1.0.0 in both directions: the KEMAC contents
differ, and `complete_psk` now decrypts rather than re-deriving.

## Timestamps

RFC 3830 defines three timestamp types (§6.6, Table 6.6): NTP-UTC (0) and NTP (1)
are **mandatory** and 64 bits wide; COUNTER (2) is **optional** and 32 bits.

mykey emits COUNTER, with the CSB ID as the counter value. Moving to a mandatory
NTP type requires a clock and a skew-tolerance policy, which also makes messages
expire — a deployment constraint rather than a pure bug fix, so it is tracked
separately.

The length of type 1 is now correct. `TimestampType::value_len()` previously
reported 4 bytes where Table 6.6 specifies 64 bits, and because
`parse_timestamp` uses that length both to slice the value and to advance the
payload cursor, a type 1 timestamp was read four bytes short and every following
payload parsed from the wrong offset. Measured at the time: types 0 and 2 parsed
correctly, only type 1 was affected, and it failed closed with a parse error
rather than silently accepting misaligned data. The variant was also misnamed
`NtpShort`; Table 6.6 type 1 is "NTP" at 64 bits, not a short form.

## Replay protection

Not implemented. Nothing records the timestamps or RAND values already seen
(§5.4), so a captured PSK-Init can be replayed and the receiver will accept it and
derive the same keys.

This needs state, which mykey currently has none of — `from_bytes` is a pure
function — so where the cache lives is an API design question rather than a
missing call.

## The "Last payload" terminator — fixed

This was the single most consequential wire-format deviation: it affected every
message in every mode. It is **fixed**, and recorded here because it is a
breaking wire change against mykey ≤ 1.0.0.

RFC 3830 Table 6.1.b assigns **0** to "Last payload", the value that terminates a
payload chain, and assigns nothing to the common header — `HDR` is never a
`Next Payload` value.

mykey ≤ 1.0.0 declared `PayloadType::Last = 255` and mapped `0` to
`PayloadType::Hdr`. Value 255 is not defined by Table 6.1.b at all. The effects
were:

- **Outbound messages were non-conformant.** Every chain was terminated with
  `0xFF`, which a conformant peer rejects as an undefined `Next Payload` value.
- **Inbound parsing worked only by accident.** The loop was
  `while next != 255 && pos < data.len()`, so a conformant `0` terminator was
  never recognised as one — parsing stopped because the cursor reached the end of
  the buffer. A chain ending before the buffer did instead resolved `0` to `Hdr`
  and failed with `InvalidPayloadType(0)`.

`Last` is now `0`, `Hdr` has been removed from the enum (it had no wire value and
was never referenced), and the parse loop terminates on the value, treating an
exhausted buffer mid-chain as the truncation it is rather than as a successful
parse.

Two consequences for callers:

- A message from mykey ≤ 1.0.0, terminated with 255, is now rejected with
  `InvalidPayloadType(255)`. Both ends of an exchange must be upgraded together.
- `PayloadType::Hdr` no longer exists. Nothing in the crate referenced it; the
  common header is represented by `Payload::Header`, which is unaffected.

## Key data sub-payload — fixed

RFC 3830 §6.13 gives key material inside KEMAC a structure: a `Next Payload`,
`Type` and `KV` nibbles, an explicit `Key data len`, and optional salt and key
validity fields. One KEMAC may carry several such sub-payloads, chained and
terminated by a "Last payload" marker.

mykey ≤ 1.0.0 wrote the TGK into `enc_data` as bare bytes with none of this
framing. `KeyDataSubPayload` now implements the full layout, including the §6.14
key validity data in both its SPI/MKI and interval forms. PSK mode emits a single
TGK sub-payload with `KV = Null`.

## Verification message — fixed

The pre-shared key and public-key methods use a verification message (`V`, §6.9;
data type 1) so the responder can prove possession of the key — this is what
provides mutual authentication. The initiator requests it via the V flag in the
common header.

mykey ≤ 1.0.0 had the `VerificationPayload` type but nothing built or checked
one, and the header flag was never set. It is now implemented as an opt-in:
`new_psk_init_requiring_verification` sets the flag, `new_psk_verification`
builds the reply, and `verify_psk_verification` checks it. The default
`new_psk_init` still requests no reply, so offline distribution over SDP or SAP
keeps working.

Per §5.2, the verification MAC covers the responder's message followed by
`IDi || IDr || Timestamp`, and the responder must echo the initiator's timestamp
rather than minting a new one — a substituted timestamp is rejected.

The `VerificationPayload` wire format was also wrong: §6.9 places an `Auth alg`
byte between `Next Payload` and the verification data, and mykey ≤ 1.0.0 omitted
it from both parsing and serialization, hardcoding a 20-byte MAC instead. This is
a breaking wire change for any V payload.

## Public-key mode

The public-key encryption method of §3.2 is not implemented. `PayloadType::Sign`
and `PayloadType::Cert` exist as enum discriminants for wire-format completeness,
but there are no corresponding payload types, and nothing parses, serializes, or
verifies them.

## What *is* interoperable

The PRF (§4.1.2), the key derivation labels and constants (§4.1.3 and §4.1.4),
the payload chain terminator (§6.1), the individual payload layouts, and the
common header fields all follow the RFC.

Pre-shared key mode — the only method RFC 3830 makes mandatory to implement, and
so the one any other MIKEY stack is guaranteed to support — now follows §3.1 for
key transport, §4.2.3 for key wrapping, §6.13 for key data framing, §5.2 for MAC
computation and coverage, and §6.9 for the verification message.

Two gaps remain before a PSK exchange is fully conformant: the timestamp is the
optional COUNTER type rather than a mandatory NTP type, and there is no replay
protection. Neither prevents a conformant peer from parsing the message.

Note that RFC 3830 publishes no test vectors, so conformance of the derivation
chain can only be confirmed by testing against another implementation.
